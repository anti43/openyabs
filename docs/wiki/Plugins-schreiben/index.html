    Plugins für OpenYaBS schreiben¶

    Plugins erweitern OpenYaBS, ohne den Kern anzufassen. Über eine einzige, einheitliche Schnittstelle — den ExtensionContext — kann ein Plugin Folgendes beisteuern:

    • Befehle (im Menü Plugins und in Alles durchsuchen über Umschalt Umschalt)
    • Eigene Suchergebnisse in Alles durchsuchen
    • Einstellungsseiten (unter Einstellungen › Plugins, über die Einstellungssuche auffindbar)
    • Eigene Tabs im Hauptfenster
    • Markierungen & Sperren in Datensatz-Ansichten (Badges im Kopfbereich, Banner mit Schaltflächen, Inhaltssperren)
    • Reaktionen auf Aktivitäten (neue/geänderte/gelöschte Datensätze, erzeugte PDF-/ODT-/E-Rechnungsdateien, Meldungen)
    • Record-Modifier (Datensätze vor dem Speichern oder Löschen prüfen, anpassen oder blockieren)
    • Eigene Vorlagen-Platzhalter ([meinplugin.feld] in LibreOffice-.odt- und .fodt-Vorlagen)
    • Journal-Exporte & Steuerberater-ZIP-Beiträge (eigene Einträge im Export-Menü des Journals und Dateien im Steuerberater-ZIP)
    • Warnungen vor dem E-Mail-Versand (Rückfrage im interaktiven Betrieb oder Überspringen im Stapelversand)
    • Ausnahmeregeln für E-Rechnungen (Fallback auf reines PDF statt ZUGFeRD / XRechnung für passende Rechnungen)
    • DSGVO-/Datenschutz-Integration (zusätzliche Aufbewahrungsfristen, Art.-15/20-Exportdateien, Bereinigung bei endgültiger Löschung)
    • Archivierte Originale für gesperrte Belege (unveränderliche Originale öffnen und gestempelte Duplikate steuern)
    • Plugin-eigene Übersetzungen (i18n) (automatische Sprachauflösung, MessageFormat-Platzhalter, kollisionsfrei pro Plugin-ID)

    Plugins lassen sich entweder als einzelnes Groovy-Skript (.groovy, ohne Build-Schritt) oder als Java-JAR (.jar, mit voller IDE- und Build-Unterstützung) entwickeln. Beide erhalten exakt dieselbe ExtensionContext-Schnittstelle.

    Wie Plugins in OpenYaBS funktionieren¶

    • Speicherort: Plugins liegen im Ordner plugins/ im OpenYaBS-Programmordner (Einstellungen › Plugins › Ordner öffnen).
    • Verwaltung: Einstellungen › Plugins zeigt alle eingebauten, Groovy- und Java-Plugins samt Zustand (RUNNING, STOPPED, DISABLED, FAILED), Anzahl der Beiträge und eventueller Fehlermeldung. Unter Plugin hinzufügen stehen Neues Groovy-Plugin…, Groovy-Plugin importieren… und Java-Plugin importieren… bereit; außerdem lassen sich .groovy- und .jar-Dateien per Drag & Drop direkt auf die Seite ziehen.
    • Start im Hintergrund: Nach der Anmeldung sucht OpenYaBS Plugins und kompiliert Groovy-Skripte in einem Hintergrund-Thread (yabs-plugins), zeigt den Fortschritt in der Statuszeile (Plugins werden geladen (2/5): …) und ruft anschließend start(ctx) der Plugins nacheinander im Swing-Event-Dispatch-Thread (EDT) auf.
    • Fehlerisolation: Wirft ein Plugin in start(ctx) eine Exception oder erfüllt minYabsVersion() nicht, werden bereits registrierte Teilbeiträge zurückgenommen, das Plugin als FAILED mit Fehlermeldung markiert, und OpenYaBS sowie alle anderen Plugins laufen normal weiter.
    • Automatisches Aufräumen & Hot-Reload: Alles, was über ExtensionContext registriert wurde, ist an die Plugin-ID gebunden und wird beim Stoppen, Deaktivieren, Neuladen, Entfernen oder bei einem Startfehler automatisch entfernt. Plugins lassen sich daher ohne Neustart von OpenYaBS entwickeln und neu laden.
    • Datenbankwechsel: Wechselt der Benutzer auf eine andere Datenbankverbindung, ruft OpenYaBS stopAll() und danach startAllInBackground() auf. Datenbankzugriffe in start(ctx) sollten daher immer mit hasDatabase() abgesichert werden.
    • Plugin-IDs & nahtloses Ersetzen: Jedes Plugin besitzt eine eindeutige, stabile id(). Zwei Plugins mit derselben ID laufen nie gleichzeitig. Wird eine neue Datei installiert, deren Plugin dieselbe ID hat wie eine bereits vorhandene Datei (z. B. der Umstieg von Groovy auf Java), stoppt OpenYaBS automatisch das alte Plugin, startet das neue und benennt die alte Datei in <Dateiname>.replaced um.
    • Dateien pro Plugin im Ordner plugins/:
    • plugins.properties – kommagetrennte Liste deaktivierter Plugin-IDs
    • <sichere-plugin-id>.properties – Schlüssel/Wert-Speicher für ctx.settings()
    • <sichere-plugin-id>/ – eigener Datenordner für ctx.dataFolder() (wird bei Bedarf automatisch angelegt)

    Groovy vs. Java: Vorteile, Nachteile und Entscheidungshilfe¶

    Sowohl Groovy- als auch Java-Plugins haben vollen Zugriff auf ExtensionContext und sämtliche OpenYaBS-Klassen. Der Unterschied liegt in Workflow, Paketierung, Startzeit und Wartbarkeit.

    Direkter Vergleich¶

    Kriterium Groovy-Plugin (.groovy) Java-Plugin (.jar)
    API-Einstieg Skriptvariablen yabs (ExtensionContext) und plugin (GroovyExtension) YabsExtension.start(ExtensionContext ctx)
    Metadaten Kopfkommentare: // @id, @name, @description, @version, @author, @minYabsVersion Interface-Methoden: id(), name(), description(), version(), author(), minYabsVersion()
    Stopp-Hook onStop = { … } oder yabs.onStop { … } stop() und/oder ctx.onStop(() -> …)
    Build-Werkzeuge Keine — reine Textdatei speichern und fertig JDK 21 + Gradle (oder Maven / javac + jar)
    Entwicklungszyklus Sofort (Strg+S im eingebauten Editor) JAR neu bauen → kopieren/importieren → Neu laden
    Eingebauter Editor Ja (Einstellungen › Plugins › Bearbeiten): Syntax-Highlighting, Zeilennummern, F5-Prüfung, Code-Snippets Nein — Entwicklung in IntelliJ IDEA, VS Code, Eclipse oder per CLI + KI-Agent
    Typsicherheit Dynamisch (Tippfehler fallen erst zur Laufzeit auf, außer mit @CompileStatic) Volle Kompilierzeit-Prüfung und IDE-Refactoring
    Startzeit Wird bei jedem App-Start per GroovyShell neu kompiliert (bei großen Skripten spürbar) Vorkompilierter Bytecode — praktisch verzögerungsfrei
    Codestruktur Eine einzelne .groovy-Datei (ab ca. 60.000 Zeichen schaltet der Editor das Highlighting ab) Beliebig viele Pakete, Klassen und saubere Schichttrennung
    Mitgelieferte Ressourcen Nicht nativ gebündelt (müssen als Strings eingebettet oder separat geliefert werden) Direkt im JAR via getResourceAsStream: .fodt-Vorlagen, i18n/*.properties, JSON-Kataloge, Icons
    Externe Bibliotheken Kein @Grab (Apache Ivy ist bewusst nicht enthalten); beschränkt auf JDK + OpenYaBS-lib/ Volle Freiheit — zusätzliche Abhängigkeiten lassen sich als Fat-/Shaded-JAR bündeln
    Mehrere Plugins pro Datei 1 Plugin pro .groovy-Datei Mehrere YabsExtension-Klassen in einem JAR (eine Klasse pro Zeile in META-INF/services/…)
    Unit-Tests & CI Über ExtensionManager.install(file) möglich, interne Hilfsfunktionen aber schwer isoliert testbar Erstklassige JUnit-5-Tests für Logik, SQL gegen H2 und Headless-ExtensionManager
    Weitergabe Eine .groovy-Datei; Benutzer können Code direkt einsehen und anpassen Eine .jar-Datei; saubere Versionierung und reproduzierbare Builds

    Groovy-Plugins – Vor- und Nachteile¶

    Vorteile: - Null Einrichtung: Kein JDK, kein Gradle, keine IDE nötig — jeder OpenYaBS-Benutzer kann in 30 Sekunden ein lauffähiges Plugin erstellen. - Eingebauter Editor: Groovy-Highlighting, Zeilennummern, fertige Beispiele (Beispiel einfügen), F5-Syntaxprüfung mit Sprung zur Fehlerzeile und Strg+S für sofortigen Hot-Reload. - Kompakte Syntax: Groovy-Closures werden automatisch in Java-Funktionsinterfaces (Runnable, Consumer, Function, Predicate, Supplier) umgewandelt. - Ideal für schnelle KI-Automatisierungen: Ein KI-Agent kann eine einzige .groovy-Datei generieren, die der Benutzer ohne Build-Tool direkt in plugins/ ablegt.

    Nachteile: - Fehler erst zur Laufzeit: Falsch geschriebene Methodennamen oder falsche Typen zeigen sich erst, wenn der jeweilige Codepfad ausgeführt wird. - Keine gebündelten Ressourcen: .fodt-Vorlagen, .properties-Übersetzungsdateien oder JSON-Kataloge lassen sich nicht sauber mitliefern. - Kein @Grab: Apache Ivy ist aus der Groovy-Laufzeit entfernt; externe Maven-Bibliotheken können nicht nachgeladen werden. - Skaliert schlecht für große Plugins: Lange Skripte verzögern den Start, sind schwer zu pflegen, und ab ~60.000 Zeichen deaktiviert der eingebaute Editor die Syntaxhervorhebung.

    Java-Plugins – Vor- und Nachteile¶

    Vorteile: - Kompilierzeit-Sicherheit: Der Java-21-Compiler erkennt API-Abweichungen, fehlende Imports und Typfehler sofort beim Bauen. - Saubere Architektur: Klare Trennung in Einstiegspunkt (*Plugin), Persistenz (*Store), reine Prüflogik (*Validator) und Oberfläche (*Ui), genau wie bei allen offiziellen Plugins. - Ressourcen & i18n im JAR: .fodt-Vorlagen, UTF-8-messages_de.properties / messages_en.properties, JSON-Kataloge und Icons werden direkt in src/main/resources/ mitverpackt. - Schneller Start & Isolation: Vorkompilierter Bytecode lädt über einen eigenen URLClassLoader. - Voll automatisiert testbar: Schnelle JUnit-5-Tests für Validatoren, SQL gegen In-Memory-H2, Übersetzungsschlüssel und Headless-ExtensionManager — ideal, damit KI-Agenten ihre Arbeit selbst per ./gradlew test verifizieren können. - Drittanbieter-Bibliotheken: Zusätzliche Abhängigkeiten können bei Bedarf direkt mit ins JAR gepackt (geshadet) werden.

    Nachteile: - Build-Toolchain erforderlich: Benötigt JDK 21 und Gradle (oder Maven). - Etwas längerer manueller Edit-Reload-Zyklus: Nach Änderungen ist ein ./gradlew jar und ein Klick auf Neu laden nötig (automatisierte JUnit-Tests gleichen das jedoch weitgehend aus).

    Entscheidungshilfe: Wann Groovy, wann Java?¶

    Groovy wählen, wenn… Java wählen, wenn…
    Du eine kleine Automatisierung (< ~300 Zeilen) brauchst: eigener Befehl, Benachrichtigung, kleine Suche, einfache Speicherregel. Du ein Fach- oder Branchenmodul baust (eigene DB-Tabellen, Dialoge, Auswertungen, Vorlagen, Exporte).
    Du eine Idee live in OpenYaBS prototypisieren möchtest, ohne eine Build-Umgebung einzurichten. Du .fodt-Vorlagen, mehrsprachige .properties-Dateien oder Datenkataloge in einer Datei ausliefern willst.
    Der Endanwender das Skript direkt unter Einstellungen › Plugins › Bearbeiten anpassen können soll. Du Kompilierzeit-Prüfung, JUnit-5-Tests, Git/CI-Workflows oder robuste Verteilung an viele Nutzer möchtest.
    Dir JDK + eingebaute OpenYaBS-Klassen ausreichen. Du externe Bibliotheken oder mehrere Klassen/Pakete brauchst.

    Nahtlose Migration: Groovy → Java¶

    Du kannst problemlos in Groovy starten und das Plugin später nach Java portieren, ohne bestehende Installationen zu verlieren:

    1. Gib in deiner Java-YabsExtension exakt dieselbe id() zurück wie zuvor im Groovy-Skript (z. B. "groovy.mein-plugin" oder deine eigene // @id).
    2. Installiert der Benutzer die neue .jar-Datei über Einstellungen › Plugins › Java-Plugin importieren…, stoppt OpenYaBS automatisch das Groovy-Plugin, startet das Java-Plugin und benennt mein-plugin.groovy in mein-plugin.groovy.replaced um.
    3. Da ctx.settings(), ctx.dataFolder() und eigene Datenbanktabellen an die ID gebunden sind, bleiben alle Einstellungen, Dateien und Daten nahtlos erhalten. (Das offizielle GoBD-Plugin nutzt genau diesen Mechanismus mit ID = "groovy.gobd-compliance".)

    Schnellstart: Groovy-Plugin (30 Sekunden)¶

    Variante A: Über den eingebauten Plugin-Editor¶

    1. Einstellungen › Plugins öffnen und Neues Groovy-Plugin… klicken.
    2. Einen Namen eingeben (z. B. rechnungshelfer). OpenYaBS legt plugins/rechnungshelfer.groovy aus einer lauffähigen Vorlage an und öffnet den Groovy-Plugin-Editor.
    3. Über Beispiel einfügen ▾ lassen sich fertige Bausteine einfügen (Befehl, Suchergebnisse, Reaktion auf neue Datensätze, Einstellungsseite, eigener Tab, Record-Modifier, gespeicherte Werte, Hintergrundarbeit).
    4. F5 (Prüfen) prüft die Syntax im Hintergrund und springt bei Fehlern direkt in die betroffene Zeile.
    5. Strg+S (Speichern und starten) speichert und lädt das Plugin sofort neu. Mit Anderer Editor öffnest du die Datei in VS Code, IntelliJ oder einem anderen Editor.

    Variante B: Datei direkt in plugins/ anlegen¶

    Datei plugins/rechnungshelfer.groovy (UTF-8):

    // @id com.example.rechnungshelfer
// @name Rechnungshelfer
// @description Zählt offene Rechnungen und meldet neu angelegte Rechnungen
// @version 1.0.0
// @author Dein Name
// @minYabsVersion 2.0.10

import mpv5.db.common.Context
import mpv5.db.common.DatabaseObject
import mpv5.db.objects.Item
import mpv5.handler.Activity
import mpv5.plugin.api.SearchResult

// 1. Befehl im Menü "Plugins" und in "Alles durchsuchen" (Umschalt Umschalt)
yabs.addCommand('Offene Rechnungen zählen', 'Zählt alle unbezahlten Rechnungen im Hintergrund', {
    yabs.background({
        def all = DatabaseObject.getObjects(Context.getInvoice())
        all.count { Item inv ->
            inv.__getIntstatus() != Item.STATUS_PAID && inv.__getIntstatus() != Item.STATUS_CANCELLED
        }
    }, { count ->
        yabs.notify("Offene Rechnungen: ${count}")
    })
})

// 2. Auf neu angelegte Rechnungen reagieren (sprachunabhängig über Context!)
yabs.onActivity({ Activity.Entry entry ->
    if (entry.kind == Activity.Kind.CREATED && Context.getInvoice().equals(entry.context)) {
        yabs.notify("Neue Rechnung erstellt: ${entry.text}")
    }
})

// 3. Eigene Treffer in "Alles durchsuchen" (läuft im Hintergrund-Thread)
yabs.addSearchProvider({ String query ->
    if (query == null || !query.toLowerCase().startsWith('web ')) {
        return []
    }
    def term = query.substring(4).trim()
    if (term.isEmpty()) {
        return []
    }
    [new SearchResult("Im Web suchen: '${term}'", 'Öffnet den Standardbrowser', {
        java.awt.Desktop.desktop.browse(new URI('https://duckduckgo.com/?q=' + URLEncoder.encode(term, 'UTF-8')))
    } as Runnable)]
})

// 4. Optionales Aufräumen beim Stoppen (Deaktivieren, Neuladen, Beenden)
onStop = {
    // Nur nötig für selbst angelegte Ressourcen (Timer, Threads, Verbindungen).
    // Alles über 'yabs' Registrierte entfernt OpenYaBS automatisch.
}

    Speichern, dann in Einstellungen › Plugins auf Neu laden klicken – fertig.

    Besonderheiten von Groovy-Plugins¶

    • Kopf-Tags: Müssen ganz am Dateianfang als // @schlüssel wert stehen. Das Auslesen endet bei der ersten Zeile, die weder leer noch ein //-Kommentar ist. Schlüssel sind case-insensitiv:
    • @id – stabile eindeutige ID (Standard: groovy.<Dateiname-ohne-Endung>)
    • @name – Anzeigename (Standard: <Dateiname-ohne-Endung>)
    • @description – Kurzbeschreibung (Standard: "")
    • @version – Versionsangabe (Standard: "1.0")
    • @author – Autor (Standard: "")
    • @minYabsVersion (Aliase: @minYabs, @minVersion) – erforderliche Mindestversion von OpenYaBS (Standard: null, also jede Version)
    • Gebundene Variablen:
    • yabs – der ExtensionContext
    • plugin – die GroovyExtension-Instanz selbst
    • Ein YabsExtension-Objekt zurückgeben: Statt yabs.* direkt im Skript aufzurufen, darf ein Groovy-Skript mit return eine Instanz zurückgeben, die mpv5.plugin.api.YabsExtension implementiert. OpenYaBS delegiert dann name(), description(), version(), author(), minYabsVersion(), start(ctx) und stop() an dieses Objekt (id() wird weiterhin vor dem Start aus @id bzw. groovy.<Dateiname> gelesen).

    2. YabsExtension implementieren¶

    src/main/java/com/example/meinplugin/HalloPlugin.java:

    package com.example.meinplugin;

import mpv5.plugin.api.ExtensionContext;
import mpv5.plugin.api.YabsExtension;

public final class HalloPlugin implements YabsExtension {

    public static final String ID = "com.example.hallo";
    private ExtensionContext ctx;

    @Override
    public String id() {
        return ID;
    }

    @Override
    public String name() {
        return ctx != null ? ctx.tr("plugin.name") : "Hallo-Plugin";
    }

    @Override
    public String description() {
        return ctx != null ? ctx.tr("plugin.description") : "Beispiel-Java-Plugin für OpenYaBS.";
    }

    @Override
    public String version() {
        return "1.0.0";
    }

    @Override
    public String author() {
        return "Dein Name";
    }

    @Override
    public String minYabsVersion() {
        return "2.0.10";
    }

    @Override
    public void start(ExtensionContext yabs) throws Exception {
        this.ctx = yabs;

        ClassLoader cl = HalloPlugin.class.getClassLoader();
        yabs.addTranslationBundle("en", "/com/example/meinplugin/i18n/messages_en.properties", cl);
        yabs.addTranslationBundle("de", "/com/example/meinplugin/i18n/messages_de.properties", cl);

        yabs.addCommand(
                yabs.tr("cmd.greet.title"),
                yabs.tr("cmd.greet.desc"),
                () -> yabs.notify(yabs.tr("cmd.greet.msg", yabs.yabsVersion())));

        yabs.onStop(() -> {
            // Eigene Threads, Timer oder Verbindungen hier freigeben.
        });
    }

    @Override
    public void stop() {
        this.ctx = null;
    }
}

    YabsExtension und Versionsprüfung¶

    Quelltext: mpv5.plugin.api.YabsExtension

    Methode Pflicht? Standard Beschreibung
    String id() Ja — Stabile, eindeutige ID (z. B. "com.example.meinplugin"). Steuert Duplikatprüfung, Ersetzen, settings(), dataFolder() und i18n-Scoping.
    String name() Ja — Anzeigename im Plugin-Manager und im Menü Plugins.
    String description() Nein "" Kurze Beschreibung (1–2 Sätze) im Plugin-Manager.
    String version() Nein "1.0" Versionsnummer des Plugins (z. B. "1.2.0").
    String author() Nein "" Autor oder Organisation.
    String minYabsVersion() Nein null Erforderliche Mindestversion von OpenYaBS (z. B. "2.0.10"). null/leer erlaubt jede Version.
    void start(ExtensionContext ctx) throws Exception Ja — Läuft im Swing-EDT; registriert alle Beiträge. Bei einer Exception wird das Plugin als FAILED markiert und alle Teilregistrierungen werden zurückgenommen.
    void stop() Nein leer Läuft im Swing-EDT beim Stoppen. Über ctx registrierte Beiträge entfernt OpenYaBS automatisch; hier nur selbst erzeugte Ressourcen (Threads, Timer, Sockets, Schlüssel) freigeben.

B. 2.0-dev oder 2.0.17-dev.123) sind Plugins für die aktuelle Major.Minor-Linie erlaubt, damit Entwickler und CI neue Features testen können. - Mit dem JVM-Flag -Dyabs.plugins.ignoreVersion=true lässt sich die Versionsprüfung beim Debuggen umgehen.

    Praxisbeispiele (Groovy und Java)¶

    1. Befehle, Hintergrundarbeit und eigene Tabs¶

    Der Swing-EDT darf nie durch Datenbankabfragen, Dateizugriffe oder Netzwerkanfragen blockiert werden. Mit ctx.background(work, then) läuft die Arbeit im Hintergrund und aktualisiert die Oberfläche sicher im EDT.

    Java:

    yabs.addCommand("Umsatzübersicht", "Öffnet einen Tab mit allen bezahlten Rechnungen", () -> {
    yabs.background(() -> yabs.select(
            "SELECT cnumber, cname, netvalue, taxvalue FROM items "
            + "WHERE inttype = 0 AND intstatus = " + mpv5.db.objects.Item.STATUS_PAID
            + " ORDER BY dateadded DESC"),
    rows -> {
        String[] cols = {"Nummer", "Titel", "Netto", "Steuer"};
        javax.swing.JTable table = new javax.swing.JTable(rows, cols);
        table.setAutoCreateRowSorter(true);
        yabs.openTab("Bezahlte Rechnungen (" + rows.length + ")", new javax.swing.JScrollPane(table));
    });
});

    Groovy:

    yabs.addCommand('Umsatzübersicht', 'Öffnet einen Tab mit bezahlten Rechnungen', {
    yabs.background({
        yabs.select("SELECT cnumber, cname, netvalue, taxvalue FROM items WHERE inttype = 0 AND intstatus = ${mpv5.db.objects.Item.STATUS_PAID} ORDER BY dateadded DESC")
    }, { rows ->
        def table = new javax.swing.JTable(rows, ['Nummer', 'Titel', 'Netto', 'Steuer'] as Object[])
        table.autoCreateRowSorter = true

})

    2. Einstellungsseiten: lokale vs. datenbankweite Einstellungen¶

    OpenYaBS bietet Plugins zwei Speicherorte für Einstellungen — wähle je nach Anwendungsfall den richtigen:

    Speicherort API Geltungsbereich Geeignet für
    Lokale Plugin-Einstellungen ctx.settings().get/set Datei plugins/<sichereId>.properties nur auf diesem Rechner Lokale Pfade (Archivordner), lokale Ports, Fenster-Optionen

    3. Eigene Ergebnisse in „Alles durchsuchen“¶

    4. Auf Datensätze und erzeugte Dateien reagieren (onActivity)¶

    Prüfe immer entry.context (sprachunabhängig) statt entry.detail (übersetzter Text), und prüfe bei Activity.Kind.FILE immer !entry.draft, damit Vorschauen oder Zwischen-PDFs nicht als endgültige Dokumente behandelt werden!

    yabs.onActivity(entry -> {
    // 1. Auf neu angelegte Rechnungen reagieren
    if (entry.kind == mpv5.handler.Activity.Kind.CREATED
            && mpv5.db.common.Context.getInvoice().equals(entry.context)) {
        yabs.notify("Neue Rechnung #" + entry.id + ": " + entry.text);
    }

    // 2. Auf erzeugte (nicht vorläufige) Exportdateien reagieren
    if (entry.kind == mpv5.handler.Activity.Kind.FILE
            && !entry.draft
            && entry.hasFile()
            && mpv5.db.common.Context.getInvoice().equals(entry.context)) {
        java.io.File exported = entry.file;
        int invoiceId = entry.id;
        yabs.background(() -> archiveCopy(invoiceId, exported),
                ok -> yabs.notify("Archiviert: " + exported.getName()));

yabs.addRecordModifier(new DatabaseObjectModifier() {
    @Override
    public DatabaseObject modifyOnSave(DatabaseObject object) throws ChangeNotApprovedException {
        if (object instanceof Item) {
            Item item = (Item) object;
            if (item.__getInttype() == Constants.TYPE_INVOICE
                    && (item.__getDescription() == null || item.__getDescription().trim().isEmpty())) {

                        JOptionPane.WARNING_MESSAGE);

                }

        }
        return object;
    }

    @Override

        return object;

    @Override public DatabaseObject modifyOnExplode(DatabaseObject object) { return object; }
    @Override public DatabaseObject executeAfterCreate(DatabaseObject object) { return object; }

    @Override public Map<String, Object> modifyOnResolve(Map<String, Object> map) { return map; }

    Ergänzt sowohl einen eigenen Eintrag im Export-Menü des Journals als auch automatische Zusatzdateien im Steuerberater-ZIP:

import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.util.Collections;
import java.util.Map;
import mpv5.handler.JournalCalc;
import mpv5.plugin.api.JournalExport;
import mpv5.plugin.api.JournalExportContext;

yabs.addJournalExport(new JournalExport() {
    @Override
    public String title() {
        return "Eigener Buchhaltungs-CSV-Export";
    }

    @Override
    public String tooltip() {
        return "Exportiert alle gezählten Journalzeilen als UTF-8-CSV mit Semikolon.";
    }

    @Override
    public void export(JournalExportContext ctx) {
        DialogForFile chooser = new DialogForFile(DialogForFile.FILES_ONLY, "journal-export.csv");
        if (!chooser.saveFile()) {
            return;
        }
        try {
            File target = chooser.getFile();
            Files.write(target.toPath(), renderCsv(ctx).getBytes(StandardCharsets.UTF_8));
            ctx.notifyExported(target); // zeigt anklickbaren Dateilink im Journal
            yabs.notify("Exportiert: " + target.getName());
        } catch (Exception e) {
            yabs.error("Export fehlgeschlagen: " + e.getMessage());
        }
    }

    @Override
    public Map<String, byte[]> adviserPackageEntries(JournalExportContext ctx) {
        byte[] bytes = renderCsv(ctx).getBytes(StandardCharsets.UTF_8);
        return Collections.singletonMap("eigener-export/journal.csv", bytes);
    }

    private String renderCsv(JournalExportContext ctx) {
        StringBuilder sb = new StringBuilder("Datum;Nummer;Kontakt;Netto;Steuer;Brutto\n");
        for (JournalCalc.Entry e : ctx.entries) {
            if (!e.counted) {
                continue;
            }
            sb.append(e.date).append(';')
              .append(e.number).append(';')
              .append(e.contact).append(';')
              .append(e.net).append(';')
              .append(e.tax).append(';')
              .append(e.gross).append('\n');
        }
        return sb.toString();
    }
});

    13. Eigene Datenbanktabellen und datenbankübergreifendes JDBC¶

    OpenYaBS unterstützt H2 (Standard, im Derby-Kompatibilitätsmodus), Apache Derby, MySQL / MariaDB und PostgreSQL.

    • ctx.select(sql) und ctx.execute(sql) sind praktisch für schnelle Abfragen, nehmen aber reines SQL entgegen und schlucken SQL-Fehler.
    • Für produktive Plugins mit eigenen Tabellen oder Benutzereingaben nutze JDBC PreparedStatement auf der OpenYaBS-Datenbankverbindung und sichere den Zugriff immer über hasDatabase() ab (wichtig für Headless-Tests und Datenbankwechsel):
    import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;
import mpv5.db.common.DatabaseConnection;

public static boolean hasDatabase() {
    try {
        return DatabaseConnection.getConnector() != null
                && DatabaseConnection.getConnector().getConnection() != null;
    } catch (Throwable t) {
        return false;
    }
}

public static Connection connection() throws SQLException {
    DatabaseConnection dc = DatabaseConnection.getConnector();
    Connection c = dc == null ? null : dc.getConnection();
    if (c == null) {
        throw new SQLException("Keine aktive OpenYaBS-Datenbankverbindung");
    }
    return c;
}

public static void initSchema(Connection conn) throws SQLException {
    // Tabellennamen immer mit eigenem Plugin-Präfix versehen!
    // Portable SQL-Typen nutzen: INT, BIGINT, VARCHAR(...), CLOB/TEXT, TIMESTAMP.
    try (Statement st = conn.createStatement()) {
        st.execute("CREATE TABLE IF NOT EXISTS myp_notes ("
                + "item_id INT PRIMARY KEY, "
                + "note VARCHAR(2000) NOT NULL, "
                + "updated_at VARCHAR(32) NOT NULL)");
    } catch (SQLException e) {
        // Älteres Apache Derby kennt kein IF NOT EXISTS (SQLState X0Y32 = Tabelle existiert bereits)
        if (!"X0Y32".equalsIgnoreCase(e.getSQLState())) {
            throw e;
        }
    }
}

    Tipps für datenbankübergreifendes SQL: - Eigene Tabellen immer mit eindeutigem Plugin-Präfix benennen (z. B. ws_, hp_, verein_, gobd_). - Benutzereingaben niemals per String-Konkatenation ins SQL einbauen — immer ?-Parameter im PreparedStatement verwenden. - Die gemeinsame OpenYaBS-Connection niemals schließen (close())! Nur eigene Statement, PreparedStatement und ResultSet per try (...) schließen. - Datenbankspezifische UPSERT-Dialekte (ON CONFLICT, MERGE, ON DUPLICATE KEY) vermeiden; portabel ist UPDATE ... WHERE id = ? und bei executeUpdate() == 0 ein INSERT INTO .... - ISO-Daten als VARCHAR(10) (YYYY-MM-DD) verhalten sich über H2, Derby, MySQL und PostgreSQL hinweg zeitzonenfrei und identisch.

    Headless-Unit-Tests mit JUnit 5 (ohne GUI!)¶

    ExtensionManager lässt sich in Unit-Tests direkt mit einem temporären Verzeichnis und einem minimalen Stub-Host starten. So testest du Registrierung, Befehle, Suchanbieter, i18n, Vorlagenfelder, Aufräumen beim Stoppen und JAR-Paketierung schnell und deterministisch:

    import static org.junit.jupiter.api.Assertions.*;

import java.nio.file.Path;
import java.util.ArrayList;
import java.util.List;
import javax.swing.JComponent;
import mpv5.plugin.ExtensionManager;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.io.TempDir;

class HalloPluginTest {

    @TempDir
    Path tempDir;

    static final class StubHost implements ExtensionManager.Host {
        final List<String> messages = new ArrayList<>();
        final List<String> errors = new ArrayList<>();
        @Override public void openTab(String title, JComponent content) {}
        @Override public void notify(String message) { messages.add(message); }
        @Override public void ui(Runnable r) { r.run(); }
        @Override public void changed() {}
        @Override public void error(String plugin, Throwable t) { errors.add(plugin + ": " + t); }
    }

    @Test
    void startetRegistriertBefehlUebersetztUndRaeumtAuf() {
        StubHost host = new StubHost();
        ExtensionManager mgr = new ExtensionManager(tempDir.toFile(), host);

        ExtensionManager.Installed inst = mgr.register(new HalloPlugin());
        assertTrue(mgr.start(inst));
        assertEquals(ExtensionManager.State.RUNNING, inst.getState());
        assertEquals(1, mgr.commands().size());
        assertTrue(host.errors.isEmpty());

        // Übersetzungen für verschiedene Locales prüfen
        assertEquals("Hallo sagen", mgr.translateForLocale(HalloPlugin.ID, "de_DE", "cmd.greet.title", null));
        assertEquals("Say hello", mgr.translateForLocale(HalloPlugin.ID, "en", "cmd.greet.title", null));

        // Befehl ausführen

        assertFalse(host.messages.isEmpty());

        // Stoppen entfernt alle Beiträge
        mgr.stop(inst);
        assertEquals(0, mgr.contributions(HalloPlugin.ID));
        assertTrue(mgr.commands().isEmpty());
    }
}

    • Eingebauter Plugin-Editor (F5): Findet Groovy-Syntaxfehler im Hintergrund und springt direkt in die Zeile.
    • Fehlermeldung im Plugin-Manager: Gerät ein Plugin in den Zustand FAILED, stehen Exception-Typ und Meldung direkt unter Einstellungen › Plugins.

    Checkliste typischer KI-Stolperfallen¶

    Beim Prüfen von KI-generierten Plugins lohnt sich ein kurzer Blick auf diese häufigen Fehlerquellen:

    1. Falsches Plugin-Paket: Immer mpv5.plugin.api.YabsExtension + ExtensionContext verwenden, niemals das veraltete mpv5.pluginhandling.YabsPlugin / plugin.Main.
    2. Fehlende ServiceLoader-Datei: Java-JARs müssen META-INF/services/mpv5.plugin.api.YabsExtension (exakter Dateiname!) mit dem vollqualifizierten Klassennamen enthalten.
    3. Kopfkommentare nach import in Groovy: Die Tags // @name, // @id usw. werden nur ganz am Anfang der Datei vor der ersten Code-/Import-Zeile gelesen.
    4. @Grab in Groovy: Apache Ivy ist in OpenYaBS nicht enthalten; @Grab schlägt fehl. Für externe Bibliotheken Java + Gradle nutzen.
    5. Sprachabhängige Vergleiche in onActivity: Context.getInvoice().equals(entry.context) nutzen statt entry.detail == "Rechnung" (sonst funktioniert es in englischer Oberfläche nicht).
    6. entry.draft vergessen: Vorschauen und Zwischen-PDFs lösen Activity.Kind.FILE mit entry.draft == true aus — beim Archivieren/Festschreiben immer überspringen.
    7. Swing-EDT blockiert: Langsame DB-Abfragen, Dateiexporte oder HTTP-Aufrufe gehören in ctx.background(work, then).
    8. Fehlender hasDatabase()-Guard in start(ctx): Bei Headless-Tests oder Datenbankwechseln kann start(ctx) ohne aktive Datenbankverbindung laufen.
    9. Gemeinsame JDBC-Connection geschlossen: DatabaseConnection.getConnector().getConnection() niemals in ein try (...) setzen — das Schließen trennt OpenYaBS von der Datenbank!
    10. Falscher Einstellungsbereich: ctx.settings() gilt nur lokal auf einem Rechner (plugins/<id>.properties); für gemeinsame Geschäftsregeln in einer Mehrbenutzer-Datenbank GlobalSettings verwenden.
    11. ChangeNotApprovedException-Konstruktor: throw new ChangeNotApprovedException(object) erwartet das DatabaseObject, keinen Text-String — Hinweise vorher per JOptionPane oder ctx.error(...) anzeigen.
    12. Unersetzte [meinplugin.key]-Platzhalter: Alle dokumentierten Vorlagenfelder bei leerem Wert mit "" statt null befüllen.

    Klassische Plugins (Legacy)¶

    Plugins älterer YaBS-Versionen (eine Klasse plugin.Main, die mpv5.pluginhandling.YabsPlugin implementiert und pro Benutzer in der Datenbank gespeichert wird) funktionieren aus Kompatibilitätsgründen weiterhin und stehen unten unter Einstellungen › Plugins im Abschnitt Klassische Plugins (Datenbank) (mit Anzeigen aufklappen). Für neue Plugins bitte ausschließlich die moderne API (mpv5.plugin.api.YabsExtension oder .groovy-Skripte) verwenden.
